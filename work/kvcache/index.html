문제

4인이 하루 반 만에 만드는 멀티 에이전트 RAG에서, 병렬로 도는 워커 하나가 예외를 던지면 같은 단계의 다른 워커 결과까지 사라졌다. 10월에 같은 과제를 Supervisor 구조로 다시 만들 때는 판정과 재작업이 늘어 LLM 호출이 상한 150에 가까워졌다.

내가 한 일

1단계에서는 통합을 맡아 그래프 층에 실패 격리 래퍼를 두고, 통합 실행 7회를 기록하며 고쳤다. 2단계에서는 게이트와 State, 실행 예산을 맡아, 팀원이 낸 토큰 예산 방향에 보완을 더해 구현했다.

결과

1단계는 7회차에 워커 6개가 모두 실제 출력을 냈다(LLM 호출 102회, 상한 150). 2단계 마지막 실행은 토큰 예산 60만 중 44만을 쓰고 경고와 함께 끝났고, 근거가 모자란 항목은 보고서와 README에 그대로 남겼다.

가치 관점: 제출할 것은 보고서였다

과제의 산출물은 마감 시각까지 내는 평가 보고서 PDF였다. 통합 실행을 시작했을 때는 아직 만들어지지 않은 워커가 있었다. 그래서 워커 하나가 실패해도 보고서는 나와야 했고, 무엇이 모자랐는지는 기록으로 남아야 했다. 2단계에서도 예산이 바닥나면 재작업만 멈추고 보고서는 끝까지 내게 했다.

구현 관점: 결정 기록

1단계: 워커의 실패를 그래프 층에서 기록으로 바꿨다

설계서 리뷰 때 '워커는 실패해도 자기 State 키에 실패를 기록한다'는 규칙을 넣자고 했고, 최종 설계서에 들어갔다. 구현 날에는 그 규칙을 그래프 층의 래퍼(graph/safe.py)로 닫았다. 워커마다 예외 처리를 맡기지 않은 것은, 워커 코드가 예외 처리를 빠뜨려도 설계서의 '빈 값으로 두지 않는다'가 지켜지게 하려는 것이었다. 미구현 워커를 스텁으로 두거나 그래프에서 빼는 안은 버렸다.

1단계: 상한을 넘으면 재시도만 멈추게 했다

번역 질의가 더해지자 병렬 단계 직후에만 LLM 호출이 약 95회였고, 설계 상한 100으로는 재시도가 돌 여유가 없었다. 상한을 넘으면 보고서 없이 끝나지 않고 재시도만 멈추게 구현했다. 실측을 근거로 상한을 150으로 올리자고 했고, 팀원이 동의했다. 정밀한 산식은 없었다.

1단계: 남의 파일은 최소한만 고쳤다가 되돌렸다

팀원의 출처 태그 검증기가 머지된 뒤 도메인·종합 워커가 통째로 실패했다. 다른 팀원의 파일이라 처음엔 정규식만 완화하는 최소 수정을 택했다. 6회차에 다시 실패했고, 동료가 먼저 낸 방식대로 태그 없는 문장을 [추론]으로 기록하게 바꿨다.

2단계: 흐름은 LLM 없는 게이트가 정한다

AI Agent 과목은 같은 주제를 Supervisor나 Orchestrator-Workers 구조로 다시 만들고, 보고서 뒤에 품질 평가와 재작업 루프를 넣게 했다. 팀은 기존 구조에서 코드가 가장 적게 바뀌는 Supervisor를 골랐다. 판정은 LLM Judge에 맡기고 다음 단계는 LLM 없는 우선순위 규칙이 정하는 설계는, AI 세션이 교안을 근거로 낸 제안을 팀이 검토해 채택한 것이다. 나는 그 게이트와 State 계약, 중단된 실행을 이어 가는 체크포인터를 구현했다.

2단계: 호출 수 대신 토큰으로 예산을 다시 짰다

판정과 재작업이 늘자 앞선 실제 실행 두 번의 LLM 호출이 상한 150 중 132회와 141회였다. 판정 한 번과 보고서 한 번이 같은 1회로 세어져, 호출 수로는 비용을 맞출 수 없었다. 팀원이 이슈에 낸 방향은 토큰 단위로, 실측의 1.5배로, 시간 상한은 게이트 밖에 두는 것이었다. 나는 '표본이 1회라 잠정값으로 적는다', '첫 실행이 최악 경로가 아닐 수 있으니 구조식에 실측 단가를 넣는다' 같은 보완을 더해 구현했고, 4명이 이슈에서 합의했다.

토큰 예산은 실측 최대값의 1.5배인 60만으로 정했다.1앞선 실제 실행 두 번의 토큰은 381,339와 397,473이었다. 시간 상한은 1,200초로 정했다(실측 580초와 603초의 1.5배는 약 900초). 시간을 게이트 밖에 둔 것은, 게이트가 시계를 읽으면 같은 State에서도 다른 결정이 나와 실행을 재현할 수 없기 때문이다.

2단계: 판정이 없으면 경고로 끝내게 고쳤다

내 게이트는 근거 판정이 없는 셀을 '충분'으로 봐서, 근거 평가가 실패하면 평가 없이 보고서로 넘어갔다. 팀원이 이 결함을 찾았고(이슈 #120), 나는 판정이 없으면 경고와 함께 끝나게 고쳤다(PR #124). 근거 평가로 다시 보내는 안은 버렸다. 그래프 모양이 바뀌는데 그 경로는 드물었고, 마감이 가까웠다.

협업

1단계는 오전 첫 PR로 State 스키마와 테스트용 fixtures를 확정해(10:41) 팀원들이 그 위에서 병렬로 개발을 시작했다. 작업 흐름을 정할 때 매 단계 AI가 다음 작업을 고르는 방식을 원한 팀원에게, 호출 수와 비용, 과제 구조를 근거로 들어 규칙표 방식을 설득했다. 1단계는 PR 리뷰 없이 각자 머지했고, 다른 팀원의 파일을 고칠 때는 커밋에 검토 요청을 남기고 구두와 슬랙으로 확인했다. 2단계에서는 실행 예산 기준을 이슈에서 4명이 처음부터 함께 정했다. PR 리뷰는 1단계 0건에서 2단계 32건(팀 전체)이 됐고, 나는 팀원 PR 14개를 승인했다.

결과와 한계

1단계 7회차에는 래퍼가 한 번도 발동하지 않았고 재시도도 없었다. 제출본은 A4 10쪽 보고서였다. 다만 통합 실행을 첫날 오전에 돌리지 않아, 다른 워커 결과가 사라지는 문제를 늦게 발견했다.

2단계 마지막 실행에서 근거가 모자란 셀 4개와 근거성(groundedness) 미달은 보고서와 자동 경고, README에 숨기지 않고 남겼다. 내 PR 15개 중 6개는 승인 없이 머지했고, 그중 3개는 마감 직전이었다.

두 단계 모두 코드는 AI(Claude)가 썼다. 1단계에서는 진단과 수정 방향을 내가 정했고, 2단계에서는 AI 세션이 쓴 코드와 이슈 글을 내가 리뷰해 올렸다.

배운 것

  • 통합 실행은 첫날 오전에 한 번 돌린다. 한계 수치는 State를 설계할 때 집계 방법까지 정한다.
  • 패턴 이름보다 흐름 제어를 누가 하느냐가 판단 기준이었다. 1단계에서 거부한 것은 LLM 라우팅이었고, 2단계 Supervisor에서도 라우팅은 결정론 게이트였다.
  • 판정 기준과 개발 중 임시 기본값은 사람이 정해야 한다. 임시 기본값은 '판정 없이 통과'가 아니라 '판정이 없으면 경고 종료'로 두고, 비용 상한은 호출 수가 아니라 토큰으로 정한다.
